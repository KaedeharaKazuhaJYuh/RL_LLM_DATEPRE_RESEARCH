## 这次解决了什么

把综合诊断拆为四类：时间窗选行、给定行集合求和、回执目标、责任边界。每类保持自身输出字段与公开输入不变，仅对照一个澄清句。四快照 × 四类 × 两措辞形成 **32 个候选提示单元**，目前仅为冻结草案，未批准实跑。

回执明确臂将“final receipt”替换为 observation.history[-1] 的 receipt_lookup；责任探针另问 history:4、8、10 的角色，避免先找错事件后把责任问题混在一起。算术探针指定全部八个公开行 ID，只检验求和，不提供正确窗口选行答案。新字段与旧综合诊断不同，不与旧 0/4 或 3/4 混比。

## 新的资格检查发现

| 探针 | 原始事实检查 | 合成反例 | 程序参考 |
| --- | --- | --- | --- |
| 时间窗 | 4 | 3 个端点变化 | 7/7 |
| 给定集合求和 | 4 | 3 个查询集合变化 | 7/7 |
| 回执目标 | 4 | 2 个改查已确认修复请求 | 6/6 |
| 责任边界 | 4 | 3 个边界变化 | 7/7 |

合计 **16 个原始事实检查 + 11 个合成事实反例**，程序参考 **27/27**。它们不是 27 个 Agent 恢复任务，也不是 27 次模型运行。

关键发现是区分度不足：固定返回旧行集合、旧求和值、旧责任模式，分别可通过原始四例的 **4/4**；对应答案变化反例中固定规则均为 **0/3**。因此，即使后续模型在原始四例全对，也不足以证明它掌握了这些规则。这里测试的是人为固定规则，**没有证据表明模型确实使用了记忆、捷径或存在泄漏**。

故意错误规则并非每例都会错。例如闭区间规则在原始四例为 0/4、合成窗口反例为 2/3；找最后 publish 的规则在原始回执为 0/4、改查该 publish 的反例为 2/2。完整通过数均冻结保留，不挑选结果，也不把偶然通过解释为正确策略。必须共同保留原始题和反例。

## 为什么本版没有继续调用 API

澄清草案主要能回答提示敏感性，尚不足以决定新的科研机制。当前原始快照的数字/责任答案没有变化；合成事实反例虽然能检出常量规则，但修改了契约或边界，旧报告和历史构造没有同步，**不能拿来评估 stop、安全完成或真实恢复行为**。

所以本版先冻结 NO-GO、批准预算 0，模块没有 live 入口。32 个候选单元不等于已批准的 32 次请求；上限草案为每次 2048 输出 token / 65536 请求字节，总输出 65536 token / 正文 2097152 字节。实际消费为 0，没有货币费用估算。判断与 API 凭据是否可用无关。

每对仅改一个句子，但句子可能澄清多项关联规则，因此只能研究措辞处理，不能宣称隔离单一认知机制。同公开数据和同上限不等于实际 token/货币成本相等。四原始状态仍只属于一个任务簇，不作泛化或显著性结论。
