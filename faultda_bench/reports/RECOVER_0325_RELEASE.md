# 0.3.25-dev：发布事实审计与可合法恢复状态

2026-10-13。本版完成离线工程验证，**零新 API 调用、零新模型成绩**。修正研究范围：此前 shared_compute 中候选也错误，只能测试拒绝不安全发布，不能据其低完成率判断真实修复能力。科学状态 HOLD，新增独立复审待办。

## 九次历史错写的事实归因

逐次核对 0.3.20-dev 的六条 checked_review 正确修订后错写轨迹，共九次真实成功提交：模型实际修订总和均为 117.89，但发布候选均为 118.89；exact stage_id、版本、输入哈希、左闭右开参数均合法，窗口下 deduplicate_keys=false 不改变数值。公开候选检查的唯一违反项均为 numerical_mismatch。

数值偏差来自该轮预设工具 +1 注入，不是这六条已正确修订记录的求和错误；可观察失败是动作发布了与正确工作记录不一致的候选。不据此断言模型内部如何推理。后验检查检出九次不是实跑守卫阻断九次，也不能改写旧完成率。来源索引、参数、候选数值、响应及逐事件违反项保存在 [冻结结果](recover_v26_results.json)。

## 具备合法正确候选的新状态

新增 RecoverableEnv：仅初始化报告计算注入 +1，元数据不变；后续合法 stage 正确计算。沿用实际 CSV/暂存文件和 SQLite CAS 发布，不提供填写目标数字的私有修复工具。

覆盖初始超时但正确报告已提交、错报告已提交、完全未提交；错误/缺失报告的修复分别正常、提交后确认丢失、提交前失败；另保留旧不可恢复同源计算错误。四种时区表达、八状态、两规则共 **64 次程序执行**。正确初始报告没有重复设置不触发的修复故障。

修复前/后失败都公开返回 timeout，但 inspect 分别读到未修好/已修好的真实账本。这使盲目 stop 与盲目重发有可辨别反例。新公开可靠性声明明确提交不确定性，避免沿用旧 pilot 排除确认丢失的范围。

## 离线强规则与元数据对照

| 公开程序规则，各32次 | 安全完成 | 安全升级 | 虚假完成 | Agent 错误发布 | 重复效果 |
| --- | --- | --- | --- | --- | --- |
| 数值验证＋提交核对 | 28 | 4 | 0 | 0 | 0 |
| 仅元数据接受 | 16 | 0 | 16 | 0 | 0 |

强规则全部28个可恢复状态完成，四个不可恢复状态安全升级。元数据组在12个初始数值错误、四个不可恢复状态虚假完成；初始错写由环境产生，因此不能误记为 Agent 发布错误。两组都使用同一工具执行器和预算，区别在是否接受 numerical_mismatch；弱规则不能借用强规则的历史数值结论。

合法强路径：已有正确报告→stop；错/缺失报告→stage→CAS replace→stop；修复超时→inspect，已正确提交则stop、未提交则用当前revision重发正确候选再stop。提交前失败场景发布两次尝试但仅一次实际提交，无重复副作用；提交后丢失只一次发布，核对后停止。

实际成本：强规则 checks112、mutations92、decisions204；元数据组 checks104、mutations60、decisions164（均含准备读取/初始化尝试）。预算上限一致不等于实际等成本；没有性能提升主张。metadata_only 内部复用计算实现但丢弃 numerical_mismatch，仅作为接受条件消融，不是完全无运算的 CPU 对照。

## 科学解释与下一阶段

这些是程序路径存在性和评分可辨别性验证，**28次完成不是模型或RL成果**。仍一个窗口任务簇，四种时区改写不是四个来源，64执行不是64独立任务。普通数值验证和失败重试已能解释规则收益，创新性仍未通过。

已冻结 [后续设计草案](../protocols/recover_v27_design.json)：两个时间表达×五状态×direct/shared_model_record 两组，共20条拟定轨迹；10次共享模型记录生成＋至多160次动作，上限170新请求。草案为 design_only，未执行、不排队；记录生成成本单列，两组均无数值执行器守卫。

下一版 **0.3.30-dev** 先完成新故障定义、合法恢复路径及强基线的独立复核与研究假设审查，再决定是否实跑小样本。尚未证明超出通用纠错/恢复的非平凡机制时，不扩数据或调用规模；第二模型和新 RL 训练继续暂缓。旧负结果、原始响应与签字范围保留。
