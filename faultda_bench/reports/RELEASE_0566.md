# FaultDA-Bench 0.5.66-dev 收尾报告

日期：2026-10-27。分支：`faultda-0.5.66-dev`。**这是 0.5.x 线的收尾版本，不开启 0.5.67。**

**2026-10-28 说明性更正：**0.5.65 已在 ALL 集上保存学习臂的逐来源结果，可按来源汇总 DEV-SEEN；本版补的是该集合的 13 臂逐 profile 全表。`k0.30_L1` 上 LinUCB 的 regret（约 0.0179）低于三族基线（约 0.0191），但高于更大规则族 F_hist_plus（约 0.0152）。各价格使用分别训练或选择的策略，不能将两点差异直接当成同一 Agent 的行为弹性。冻结结果和原实验数值未改动。

本版补充 0.5.65 已登记的 DEV-SEEN 逐 profile、全策略对照，并根据结果重新评估这条线。

## 1. 为什么是这一格

0.5.65 的 Gate 0 地图有 8 个 regime、3 个实例集。预注册的主 regime 是 `k0.30_L3`，取自 `dev_syn`（合成形状）。在该格上最佳固定规则的归一化 regret 为 0.0315 ≤ ε = 0.05，即代价结构可被 9 单元查表绕过。

同一份文件第 25–27 行记录了另一件事：`DEV-SEEN`（24 个真实已见切片）在 `k1.00_L3` 上 `min_fixed_r = 0.1801`，远大于 ε。

0.5.65 已保存全部开发集的学习臂逐来源结果，以及 DEV-SEEN 的固定规则和 DP 地图；此前没有在单一 DEV-SEEN 产物中逐 profile 展示本版的 13 臂全表。`k1.00_L1` 与 `k1.00_L3` 的三族归一化差距均超过 ε，后者是该表中最大的格子。

本轮补上：`dev_seen` × 8 regime × 13 arm × 24 profile = 192 格，2,496 个 (格, arm) 期望值。全程离线，0 次 API 调用，¥0，CPU 608 秒。

## 3. 四个结果

### 3.1 固定任务集上的价格与 headroom

同一批 24 个 profile、同一套工具、同一份数据，只改 κ：

`0.0006 (κ=0.03) → 0.0022 (0.10) → 0.0100 (0.30) → 0.1801 (1.00)`

跨度约 290 倍（`0.180086 / 0.000621`）。这只是同一开发集、L=3 及既定规则族下的四点比较；κ ≤ 0.10 时三族最佳规则接近 DP，其他策略仍可能明显更差。κ = 1.00 时的 0.1801 是相对 DP 期望效用的归一化差距，不是实际收益百分比。

0.5.65 预注册主设置是合成集的 `k0.30_L3`，三族差距约为 0.0315；这里 DEV-SEEN 同一 regime 约为 0.0100。小差距限制了相对基线的改进空间，但不能仅据此认定学习方法的成败原因。

### 3.2 高价格格子与其他格子的学习策略

在本表差距最大的 `k1.00_L3` 上：

- `thompson` = 0.1801，与 bf 完全相同，未回收一个点；
- `linucb` = 0.2031，比 bf 差；
- `q_only` = 0.3872，比 bf 差一倍以上。

这只说明最高价格、L=3 这一格的结果。`k0.30_L1` 中 LinUCB 为 0.0179，低于三族基线 0.0191；但 F_hist_plus 为 0.0152，仍优于 LinUCB。该事后开发集差异没有独立样本或显著性证据，不能概括为所有八格均未超过三族基线，也不能据此宣称泛化提升。

### 3.3 min_fixed_r 是约定值，不是最小值

`witness.py` 第 235–243 行，`min_fixed_r` 只在 `F, F_size, F_hist` 三族上取最小；`F_hist_plus` 虽然注册在 `FAMILIES` 里、也算了 `regret`，但被排除在 argmin 与 min 之外。本轮实测该族在**每一个** regime 上都不劣于 bf：

| regime | bf (F_hist, 3 单元) | F_hist_plus (66 单元) | 回收差距 |
|---|---:|---:|---:|
| k0.30_L1 | 0.0191 | 0.0152 | 20.4% |
| k1.00_L1 | 0.0999 | 0.0876 | 12.3% |
| k1.00_L3 | 0.1801 | 0.1636 | 9.1% |
| k0.30_L3（主） | 0.0100 | 0.0100 | 0% |

预注册未将其列入三族基线：`dev_seen` 有 24 个 profile、该族有 66 个单元；`dev_syn` 有 6 个 profile、该族有 198 个单元。它按 `(整个历史计数, 规模桶)` 建表，容量高于 F_hist；这些单元不是 profile ID，但在同一开发集选表存在过拟合风险。

原代码与报告没有写清这个约定。读者看到的 `min_fixed_r` 会被读成"所有固定规则里的最小值"，而它其实是"三族固定规则里的最小值"。对这里的阈值判断，两种约定得到相同结果：DEV-SEEN 的 `k0.30_L3` 为 0.0100 ≤ ε；`k1.00_L3` 的 18.0% 或 16.4% 均大于 ε。规则定义仍会影响具体差距，不能推广成所有结论都相同。

推论比这个修正本身更有用：**你测到的"自适应的价值"取决于你把对手类限定得多宽。** 一个更细的查表就吃掉了 9% 到 20%。

### 3.4 两个价格点的计费量比较

归一化计费量 `l/b_ref = spent/κ`（每 profile），以及 κ 从 0.10 升到 1.00（价格 ×10）时两点计费量的对数比值。原报告称其为“弹性”，但因各价格下策略不同，这不是固定 Agent 的行为弹性：

| arm | l (κ=0.10) | l (κ=1.00) | 对数比值 (L=3) | 对数比值 (L=1) | regret 变化 |
|---|---:|---:|---:|---:|---|
| bf | 0.990 | 0.547 | −0.26 | −0.38 | 0.0022 → 0.1801 |
| F_hist_plus | 0.990 | 0.580 | −0.23 | −0.39 | 0.0022 → 0.1636 |
| thompson | 0.990 | 0.547 | −0.26 | −0.38 | 0.0022 → 0.1801 |
| linucb | 0.992 | 0.449 | −0.34 | −0.40 | 0.0025 → 0.2031 |
| **q_only** | **0.771** | **0.033** | **−1.36** | **−1.47** | **0.3864 → 0.3872** |

`q_only` 的归一化计费量在两个设置间约降 23 倍，对数比值的绝对值约为所选固定规则的 4–5 倍；它的归一化 regret 两端接近但并不相同（0.3864 对 0.3872）。

两档使用分别训练或选择的策略，不是对同一个已固定 Agent 施加价格干预；`spent/κ` 是归一化计费量，也不是检查次数。不同 κ 下的最优值和归一化分母同时变化，因而不能只凭两端 regret 相近就断言绝对效用没有变化或策略无法改进。

## 4. 撤销一条自己的假设

本评估在跑这轮之前写下的预测是：**"检查行为对价格不敏感（|ε| < 0.2），理论最优 |ε| ∈ [1,2]"。**

这组**两点、策略随设置变化的描述性比较**与原定数值预测不一致；它不是对真实 Agent 价格行为或 DP 检查次数的因果检验。该预测不再作为已证实假设。

后续如研究价格响应，应固定任务与工具、明确价格是否展示给模型，并区分检查次数、计费量、绝对效用和归一化 regret；当前数据不能给出模型行为弹性结论。

## 5. 边界（本版不主张什么）

- 24 个**已见开发 profile**，不是独立测试；`Auto MPG` 与 `Glass` 已在本项目中被查看，不能再作为留出来源。
- 单一模型族（`rev1` latent model），`d1` 模型未在本轮重跑。
- 环境是自建的。**本版没有任何外部基准上的模型数据**，因此关于"agent 在真实任务中的行为"一个字的结论都不能下。
- `F_hist_plus` 的容量更大（66 vs 3 个单元）；这组对比不能单独证明容量是优势的原因，也不能用来支持"自适应有价值"。
- 3.4 的对数比值只使用两个价格点（0.10 与 1.00），且策略可随价格变化；不构成固定 Agent 的弹性曲线估计。

`acceptance_v48.json` 钉住 717 个文件。其中 7 个在 0.5.65 开发期间被改写，每条都在 `acceptance_v49_ci.json.superseded` 里带着原始字节（归档于 `ci565_original_bytes.json`）与修正后的摘要——也就是说，漂移是被**证明**过的，不是被豁免的。

这 7 条里有一条是 `tests/test_faultda_vericost565_release.py` 自己：它既钉住自己，又断言"当前版本号在 README 第 6 行、CHANGELOG 首行"。版本号一改，这个文件必须改；一改，摘要就不匹配；于是必须更新它那条 `corrected_sha256`，同时不动归档原件。三步缺一，CI 就红。

**我第一版缺了两步，而且把它判错了。** 我在报告里写"这处红在本分支 HEAD 上本来就失败、基线同样复现"——不成立。基线在 CI（Linux）上是全绿的；我用 Windows 本地复现当成了基线证据，混淆了两件不同的事：

| 观察 | 在 Linux CI 上 | 在 Windows 本地 |
|---|---|---|
| 基线 `7f0d112` | 绿 | 1 个失败 |

处置：更新 `corrected_sha256`、把 `tests.test_faultda_vericost566_release` 登记为第 78 个模块、归档原件不动，并新增两项守卫钉住这两件事（`FrozenCatalogTests`）。**清单本身仍然不重写**——它不是重盖章，只是把 0.5.65 的接受范围标注为"在本分支 HEAD 上已被取代"。
