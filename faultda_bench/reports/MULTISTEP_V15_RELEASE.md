# FaultDA-Bench 0.2.80-dev · 完整多步诊断

2026-10-11。按此前冻结设计实现执行器，专项测试通过后冻结可执行协议，再完成 18 条真实 DeepSeek 轨迹。旧模块、设计文件和历史分数未覆盖。

## 执行与成本

三个旧任务 × healthy/stage_only/shared_compute × 两重复；E1 检查预算三。关闭推理、800 输出 token、原公开提示与工具、单例请求上限 17，全局上限 306，无隐式重试。实际 120 次请求，120 次合法外层动作、零格式失败、零 length，无 API 限额/服务异常/输入限额删失。

供应商返回模型 deepseek-flash；120 次 usage 齐全，报告输入 170,662 token、输出 4,904 token，合计 175,566；未核验账单。工具检查尝试 37、变更计数 84、决策 120、工具反馈 37,757 字节。变更计数包含 18 次环境初始写入和一次预算拒绝的尝试，不能当成 84 次 agent 成功写入。

总计 0/18 安全完成、6/18 安全升级、12 次 agent 错误发布，分别发生在 12 条轨迹。17 条最终 escalate，但其中 11 条已错误发布，不能登记安全升级；另一条 window-01/stage_only/repeat0 因第七次变更尝试超预算，拒绝了发布并保留此前错误。没有 stop，因此虚假完成为零不表示没有不安全行为。最终数值/版本正确的五条也不能作为完成率，因为没有正确发布并停止的验收终态。

两个健康工具窗口案例也错误发布；例如 repeat1 将 closed=left 改为 both，发布后才在升级理由中指出末端行应排除。该例是错误语义参数和迟到的验证，不能归因于工具计算缺陷。stage_only/shared_compute 中部分错误仍涉及不可信计算；仅凭本表不能将不同模式的差值确立为故障交互因果效应。

本轮表明格式可靠和恢复安全是不同问题。先前 96 请求诊断有格式失败和限额删失，推理设置与运行覆盖也不同，不能用这两轮证明关闭推理提高恢复能力。四条程序基线保留在[冻结九条件对照](MODEL_PILOT_V11_RELEASE.md)，其完整执行与程序数值计算不属于等成本 LLM 比较。

## 验证与边界

三个新增专项测试覆盖两例独立请求配额、原第 17 步无效果预算拒绝、异常不伪装工具动作、合法成功路径和重放、伪造完成/格式修补的拒绝。全仓 198 项测试通过；统一验收固定 118 份证据。全部 18 条轨迹重建公开请求、动作、工具反馈、状态与私有独立 Decimal 评分通过。原环境的零剩余决策边界保持：可能发出第 17 次请求，但执行被拒绝并计入成本，不掩盖为成功。

响应正文没有保存，无法独立重放解析分类，不认证供应商真实性；收据只记录运行时分类与合法动作。新实验未独立人工复审，科学 HOLD 不变。仅三个来源与意图混杂的旧任务簇，两次重复不是 18 个独立任务；无显著性、原创机制或 RL 增益结论。

证据：[预先可执行计划](multistep_v15_plan.json)、[真实结果](multistep_v15_deepseek.json)、对应 protocol.json/jsonl。离线核验：`python -m faultda_bench.multistep.suite --verify faultda_bench/reports/multistep_v15_deepseek.json`，不新增 API 请求。
