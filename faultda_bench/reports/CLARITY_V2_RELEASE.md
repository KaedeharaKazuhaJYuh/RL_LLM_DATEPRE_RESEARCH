本轮完成两件事：纠正首版契约的说明歧义，并用同题对照检查其影响；将分组和版本意图交叉应用到三个来源。全部是历史开发数据，不是最终测试，也没有模型训练。

## 说明修正与解释更正

原契约使用原始测量列名，返回数据却统一使用 value；此外，非分组任务的通用输出字段仍描述为 group -> total。新契约明确别名和输出结构。**旧 4/12 不能简单解释成模型缺乏恢复能力**；但说明问题是否造成失败，必须单独验证，不能凭观察推断。

旧版代码、原始协议、结果和评分全部保留。新对照只改变 input_binding 与 output 两个公开字段，工具行为和 oracle 测试逐条件一致。两项说明一起改变，因此只能讨论组合干预，不分辨单字段贡献。

## DeepSeek 配对诊断

3 个旧实例 ×4 C/S 条件 ×2 说明版本，共 **24 episode /12 对**。两臂交错，模型与系统提示相同，工具预算相同；说明变长会改变 token，不能称为完全等计算成本。服务返回 `deepseek-flash`。

| 观察 | 原说明 | 明确说明 |
| --- | --- | --- |
| 契约完成 | 4/12 | 4/12 |
| 安全完成 | 4/12 | 4/12 |
| 最终产物正确 | 12/12 | 10/12 |
| 升级 | 8/12 | 8/12 |
| 错误完成声明 | 0 | 0 |
| API 请求数 | 68 | 63 |
| 服务报告 token | 81,954 | 78,942 |

配对完成差 **0**：4 对均成功、8 对均失败，没有仅某一臂成功的对。共 **131 请求、160,896 token**；无服务错误、解析错误或请求上限耗尽。单次、三个实例的结果不能支持统计显著性，也不能把少量调用减少称为稳定效率提升。

结果不支持“补充这些说明便可解决升级”的假设。明确说明臂还留下两份错误终态，不能只报完成率相同而忽略这一点。修正说明是接口质量改进，**不是模型效果提升**。

逐条事后审计发现：两臂所有升级轨迹都曾得到正确的 stage 候选；原臂 8 条的最终产物也正确，新臂 6 条终态正确、2 条有正确候选但未完成正确发布。这将下一诊断收窄到“如何使用已有候选及决定发布/结束”，仍不能据此声称已识别模型内部原因。[可复算诊断](clarity_v2_diagnosis.json)

## 跨来源离线验证

24 题 =3 来源 ×2 意图 ×4 变体；Auto MPG、Glass、Occupancy 各有分组和版本任务，采用其自然类别列作为业务键。窗口任务不进入这个交叉设计，因为前两份来源没有真实时间戳。合成维表重复和版本修订明确标注，不称为原数据的真实业务事件。

共 **2,304 episode**。检查预算 4 时，每个证据条件含 24 题 ×4 故障条件 =96：

| 基线 | E0 完成 | E1 完成 |
| --- | --- | --- |
| 全升级 | 0/96 | 0/96 |
| 盲重试 | 24/96 | 24/96 |
| 通用提交验证 | 48/96 | 48/96 |

| 任务语义检查 | 96/96 | 96/96 |

强基线在全部来源×意图单元均通过，交互量仍为 0。解除了一对一来源/意图混杂，不等于证明来源泛化；仍只有三个已见来源，变体和条件相关。没有获得支持额外耦合失败的新证据，不应继续仅靠扩题量宣称原创贡献。
