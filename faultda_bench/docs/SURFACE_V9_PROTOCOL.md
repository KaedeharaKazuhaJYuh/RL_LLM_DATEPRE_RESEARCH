# 工具返回证据与基线完整性 · 0.2.50-dev

日期：2026-10-11。版本从 0.2.35-dev 跳至 0.2.50-dev，按约定避开末段 40–49。继承 V5 基线不变。

## 接口审查发现

| 工具 | 实际公开返回 | 对可观测性的影响 |
| --- | --- | --- |
| status | revision、active_count | 提交状态，不包含数值正确性答案 |
| inspect / E0 | 活跃报告、revision、输入版本、维表、catalog | 在静态状态下，其内容覆盖其他三类只读工具的相关信息；同一次检查的计数不反映返回体积 |
| inspect / E1 | 活跃报告、revision；没有输入与 catalog | 输入和版本目录仍可由各自工具获取 |
| inputs | 版本化输入与维表 | 不直接告诉 requested snapshot/latest 的绑定 |
| catalog | 最新与快照版本标识 | 不直接提供数值参考 |
| stage | stage_id、绑定版本、参数、输入哈希、计算输出 | **带有数值参考证据的有成本写操作**；不能只统计检查数忽略它 |

上述结论由当前环境代码和真实工具轨迹核对，只适用于本轮静态、无工具计算缺陷的范围。E0 信息覆盖不意味着不同耗时、响应字节或动态状态下完全等价。

既有强规则先获取输入再自行计算；它不是已证明穷尽全部合法工具路径的最优策略。暂存参考基线只读取公开观察，不取得任务对象、参考 oracle 或故障标签。

## 冻结对照

运行前保存 `surface_v9_results.protocol.json`，固定全部代码/来源哈希、任务快照、假设和 144 个单元：三个旧实例 × E0/E1 × 检查预算 1/2/3 × 提交确认丢失有无 × 初始语义错误有无 × 两种规则。

`read_reference`：沿用既有 task_semantic 规则，先 inspect、catalog、inputs，再验证/修复。

`stage_reference`：E0 已有完整输入时沿用旧规则；E1 时 inspect、catalog、stage，把合法正确参数生成的候选与当前报告的版本、输入哈希、输出比较。报告已正确则停止；否则公开 CAS 替换。暂存计入写成本，没有隐藏的 inputs 调用。新候选受同样工具权限与预算约束。

两臂使用同样的原始环境、数据、公开权限、故障和 Decimal 私有评分器。这里**改变了完整基线算法**，不属于只改变检查分配的严格消融。结果不能与第八版分数混池。

主比较：E1、预算 2 的安全完成，按三类任务分别核对。成本诊断：预算 3 下，原报告正确/错误分层，分别报告 checks、mutations、decisions、response_bytes。不把共同检查预算称为总体等成本，也不测定耗时或模型 token。

## 限制与停止条件

- 三个旧任务与来源绑定，144 个单元不是独立任务样本；新实验未独立人工复审。
- stage 的计算在本环境内可信，fault 只扰动参数与提交确认；没有注入 stage 计算错误、源数据并发变化或伪造返回。暂存结果不保证现实工具正确。
- 没有证明两次检查为最少，也没有穷尽重算后直接替换等其他合法规则。不称其成本全局最优。
- 新路径是更完整的强基线，不作为原创方法或模型增益。科学 HOLD 保持，不据此增加训练、API 或数据来源。

后续信息选择假设必须同时面对两条强规则，并公平明确 stage 返回证据与写权限。否则模型“改善”可能只是使用了遗漏的参考计算工具。
