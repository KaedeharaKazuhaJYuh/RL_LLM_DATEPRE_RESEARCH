# 九条件真实模型诊断：接收与后续约束

日期：2026-10-11。执行使用第十一开发版已冻结的协议与代码，结果文件保留 `0.2.60-dev` 协议版本；接收与统一验收版本为 `0.2.65-dev`。不修改已冻结提示、动作接口、规则或评分器。

## 记录范围

固定三个旧任务 × healthy、stage_only、shared_compute，共九条件；E1 检查预算三，统一公开可靠性说明，DeepSeek 单次输出上限 800 token、请求超时 45 秒、全局最多 96 次实际尝试、无隐式重试。逐条件保存轨迹、动作、公开提示哈希、供应商报告的 usage/model/响应编号。输出路径与离线对照分开。

全局限额会使后面的条件被删失；必须报告每条件实际发送数、限额终止及完全没有发出请求的条件，不能把它们说成模型能力失败，也不能删掉后重新计算一个成功率。单次重复请求是模型的新决策，不是自动重试。

离线重放核验公开观察、提示哈希、工具反馈、状态更新、历史副作用与独立评分，不再次请求模型。该核验不认证供应商响应来源或账单，也不能还原未记录的响应正文与结束原因。

## 格式问题诊断边界

`parse_error` 同时涵盖空/无效 JSON 与动作 schema 不符合要求。供应商报告 completion_tokens 达到 800 只是输出截断的线索；本协议没有保存 finish_reason、正文或 reasoning_content，不能确认截断，也不能区分具体 schema 错误。不能将推理 token 计为额外完成 token 再次相加。

本轮保持这些设置完成计划，不修补历史返回、不筛选失败。不据此声称可靠性提示提升、故障交互新机制或 RL 改善。三个任务簇与来源/分析意图仍混杂，九条件不是九个独立任务。

## 下一阶段

1. 冻结独立接口诊断协议，记录结束原因、是否为空、JSON 解析与 schema 失败类别、有效动作率及 token/延迟；保持敏感内容不入日志。先用离线替身测试各失败类别。
2. 明确固定推理模式，再做小规模配对输出预算诊断；共享任务、工具、提示与顺序。预算变化带来的收益属于接口/系统配置收益，不能称模型或 RL 提升。
3. 动作格式稳定后重新冻结完整九条件预算与重复设计；旧记录保留，不能续写当前报告或混池。
4. 将新协议、程序反例与实际失败轨迹交独立复审；第二模型与训练继续暂缓，科学 HOLD 保持。
