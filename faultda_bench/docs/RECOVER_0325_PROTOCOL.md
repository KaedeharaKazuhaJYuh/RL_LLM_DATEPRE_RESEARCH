# 0.3.25-dev：合法恢复、提交不确定性与发布事实审计

本版为离线工程验证，零新 API 请求、零新模型成绩、零新 RL 训练。冻结 recover_v26_results.json 包含协议/代码哈希、64 条实际工具轨迹、私有评分及九次旧发布的公开证据审计。科学 HOLD。

## 环境与故障

四种等价时区表达×八个状态×两个公开规则，共 64 条。八状态为：初始超时但正确报告已提交；初始超时且错误数值已提交；其修复确认正常/提交后丢失/提交前失败三种；初始超时未提交，修复同样三种；旧同源不可恢复计算错误。正确初始报告不重复设无实际修复的确认丢失条件。

新 RecoverableEnv 仅在初始化计算时注入 +1 数值错误，版本、参数和输入哈希保持正确；随后合法 stage 正常计算。既有 SemanticEnv 的 CSV 文件、暂存文件和 SQLite 提交路径沿用，不允许直接填写目标数字或私有修复。旧 shared_compute 对照保持候选也错误，应升级而非冒充可修复。

修复提交前 TimeoutError 在 _commit 的 agent 路径且任何账本/request 写入前注入；原执行器仍计准确一次发布尝试和决策，公开错误统一为 timeout，response_bytes 按真实返回内容修正。修复提交后确认丢失沿用旧环境：实际账本已更新但返回 timeout。两种公开发布结果相同，随后 inspect 得到不同真实状态。

新公开 reliability_contract 明确初始/修复超时不能证明提交，须核对账本；不再使用旧 pilot 中“确认丢失不在范围”的声明。不暴露私有 profile/故障标签。原始数据不可变、无并发、没有 OS 任意代码工具。

## 同执行器规则对照

两规则都只接收序列化公开观察，先 inspect/inputs/catalog 三次，检查总预算四、mutations 总预算六（含初始化尝试）、decisions 十六，后续最多八动作。数值规则基于公开 Decimal 参考检查当前报告及请求指向的确切候选；metadata_only 用相同绑定验证但忽略 numerical_mismatch，历史判断也不得借用强数值结论。

正确报告直接 stop；合法错报告 stage→CAS replace→stop；修复超时 inspect 后，已正确提交则 stop，未提交则用当前 revision 重发原正确候选。不盲目追加发布、不增加私有权限。无正确候选则 escalate。相同预算上限不等于实际成本相同，逐项报告 checks/mutations/decisions/response_bytes。

metadata_only 内部复用绑定检查实现，计算后丢弃数值不匹配项；不是完全没有程序运算的计时对照，也不主张性能收益。仅 acceptance predicate 的数值判断差异用于这些受控案例。

## 历史事实与科学边界

从 handoff_v25 全部 checked_review 实际修订正确且发生错写的六条轨迹取九次真实成功提交，逐次核对 source_index、exact stage_id、公开参数/候选值、修订记录和检查违反项。后验检查不是重新运行模型守卫，不能据此计算新的系统完成率或 guard 因果收益。

仍仅一个任务簇。规则成功证明存在合法路径和评分可辨别，不证明模型成功、研究创新或泛化；新增独立人工/科学复审待办。本地哈希/固定提交不认证供应商响应或外部时间戳。

下一阶段模型试验仅为 design_only 预注册草案；未执行、不自动消耗 API，须先完成合法路径、可靠性声明和强对照的独立复核，再作研究决策。
