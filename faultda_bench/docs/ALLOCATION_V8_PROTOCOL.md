# 检查分配负对照 · 0.2.35-dev

目的：确认固定、随机和按需检查的差异是否仅来自检查顺序，避免将现有强规则重新命名为创新方法。本轮是工程负对照，不是新的学习策略或科学确认实验。

## 冻结设计

执行前保存 `allocation_v8_results.protocol.json`，固定代码/来源哈希、任务快照及 576 个执行单元：三个旧实例 × E0/E1 × 提交确认丢失有无 × 语义错误有无 × 检查预算 1/3 × 四臂 × 三个种子。三类意图分别绑定三个旧来源，仍有来源混杂。种子和故障条件重复不能作为新增独立样本。

四臂共享公开观察、工具权限、语义计算、暂存/CAS 修复、停止和升级条件，均使用现有 `task_semantic` 执行器；只替换执行器请求检查时的工具选择。

| 臂 | 检查分配 |
| --- | --- |
| fixed | 按 inspect、inputs、catalog 固定顺序 |
| random | 同三个工具，种子 0/1/2 打乱，无放回；只在确需检查时调用 |
| conditional | 原执行器依据公开历史选择检查 |
| strong | 同样合法信息的现有强组合规则 |

conditional 与 strong **有意使用同一选择器**，零差值应成立；不把这一结构性负对照包装为发现。固定顺序预先为 inspect 优先，不事后挑选最弱规则。故障标签、参考答案和私有台账不进入选择器。

## 成本与判定

主报分任务簇、证据等级、预算和臂的安全完成及实际 checks、mutations、decisions、response_bytes。不填满预算，不额外调用无用工具。初始化写成本按旧环境计入。程序计算没有模型 token，API 调用为零；本轮没有测定耗时或资源性能，不宣称总体效率提升。

共同预算上限不是总体等成本。另列四臂实际检查次数相同的单元数量，仅作探索诊断；后验匹配不是因果识别，不忽略写入和响应字节差异。预算上限 1、E0 随机未完成的运行与成功修复运行有不同写成本，也不能称总体等成本收益。

可证伪的后续候选要求：预先实现不同于强规则、只用合法证据的选择器，在三类任务簇分别比较安全完成与实际成本；超出强规则且不能由资源或计算帮助解释的差异，才进入独立科学验收。当前候选与强规则相同，不具备这一条件。

停止条件：当前负对照若零差值且无未解释强规则失败，维持 HOLD，不增加 API、来源或训练。下一步先审查是否存在对所有臂公平、需要选择信息且强规则无法直接解决的任务假设；若不能构造，收束为工程复现工具。
