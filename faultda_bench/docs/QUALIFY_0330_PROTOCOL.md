# 0.3.30-dev：重复故障与强策略资格核验

本版仅程序资格核验，不运行模型 API。两个时间表达×正常/一次提交前失败/提交后确认丢失/连续两次提交前失败×检查预算3/4/5×三种恢复策略，共72条冻结轨迹；另保存两对公开观察相同、真实提交不同的核验状态。

新 QualificationEnv 扩展而不改写旧 RecoverableEnv，始终使用同一初始 +1 错报告、健康合法 stage、实际CSV/SQLite和CAS。连续失败在 agent _commit 路径、任何账本/request 写入前注入，沿用准确计费和公开 timeout 返回。公开可靠性声明说明失败可重复，不暴露故障次数或私有 profile；无并发、原始源不可变。

## 三种公开策略

- inspect_first：保留上一版数值强规则，失败后优先inspect，再停止/重发，证据不足则升级。
- retry_once_reconcile：仅对已公开验证的正确候选，失败后原参数CAS重试一次；仍失败再inspect。每个最近inspect后的区间只允许一次盲重试，不无界重发。读取与写入均按原工具预算计费。
- retry_then_stop：同样重试一次，但第二次失败后直接stop。该策略故意测试“重试保证收敛”假设，不能视为合格强规则。

所有策略在同一执行器、相同预算上限和可见信息下运行；改变的是完整恢复策略和重试顺序，不是仅检查分配。实际cost不同，不能归因纯检查选择或称等实际成本效果。

## 可观察性核验

两个时间表达中，提交前一次失败和提交后确认丢失在inspect前具有逐字相同的公开history/remaining/反馈；实际账本不同。inspect后强规则应分别publish与stop。仅证明这两种观察对立即stop不足，不证明inspect是唯一可能策略或最省成本；安全CAS重试也能提供信息。

重复失败使无条件“重试后stop”产生虚假完成。此前仅单次失败时它可在有限终态评分中通过，因此不能从覆盖较弱的成功轨迹推断证据充分或一般安全。评分仍按实际结果归因，不事后修改旧成绩。

## 模型执行决定

原 recover_v27_design.json 是旧冻结草案，保持字节不变。本轮它的独立人工/科学复审仍pending，且缺少重复失败与retry_once_reconcile强基线。当前 model_execution_decision=not_ready；零新API，不把程序核验填成人工批准。新的提案仅design_only，不是排队任务或供应商调用授权凭据。

仍一个窗口任务簇，不主张显著性、泛化、学习机制或RL提升。固定提交/本地清单只提供一致性与复审材料，不认证供应商响应或外部发布时间。
