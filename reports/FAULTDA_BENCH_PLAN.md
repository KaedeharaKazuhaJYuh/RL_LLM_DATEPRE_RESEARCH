# FaultDA-Bench 研究规划

## 定位

FaultDA-Bench（Fault-aware Data Analysis Agent Benchmark）面向“状态不确定性与故障恢复的可验证数据分析 Agent”评测。它从当前项目的训练环境中独立出来，目标不是再训练一个模型，而是建立一个可复现、可扩展、能区分规划错误与环境故障的公开基准。

V5.0.15-beta.2 完成后，从稳定提交创建独立分支 `faultda-bench`。分支只接收基准协议、数据适配、评测器、基线和文档；模型训练实验仍保留在 `v5`，避免基准题目被训练结果反向调整。

## 核心研究问题

1. Agent 能否识别“动作尚未提交”“动作已提交但确认丢失”“发生了部分写入”等不可直接从单条错误消息判断的状态？
2. Agent 能否在不重复副作用的前提下选择检查、重试、继续或终止？
3. Agent 的数据分析结果是否经过真实 CSV 产物和独立验证器确认，而不是只生成看似合理的文字？
4. Agent 在新来源、新措辞、新工具组合和未见故障时是否保持恢复能力？
5. 模型是否把环境故障误认为自己的动作错误，或把动作错误误认为环境故障？

## 基准任务结构

每个 episode 由五层组成：

| 层 | 内容 |
| --- | --- |
| 数据层 | 公开 CSV、来源许可、原始文件摘要、派生文件和列类型 |
| 分析层 | 去重、缺失值、类别规范化、异常值、日期、聚合、相关性、滚动统计等组合 |
| 状态层 | 未提交、已提交、确认未知、部分写入、输入未改变、产物已验证 |
| 故障层 | 提交前超时、提交后确认丢失、读取失败、部分写入、进程崩溃、迟到结果、重复提交风险 |
| 语言层 | 中文、英文、同义改写、参数表达变化和提示长度变化 |

基准分为四种任务形态：

- **Recovery**：给定首个操作和后续分析目标，评测故障恢复决策。
- **Planning**：从完整请求自主选择工具序列。
- **Verification**：检查产物、输入哈希、列结构和统计答案，决定是否可以结束。
- **Composed**：把规划、故障恢复和最终验证放在同一条多步轨迹中。

每个任务必须有状态机、工具调用上限、时间上限、输入哈希和独立 oracle。模型不能读取 oracle、故障标签、私有回执内容或评测门槛。

## 状态不确定性设计

故障消息应尽量相同，把可辨识信息放在合法的检查动作中。基准至少包含以下成对干预：

| 干预对 | 共同观察 | 真正差异 | 期望行为 |
| --- | --- | --- | --- |
| before-commit / after-commit | 超时或确认丢失 | 是否已产生持久产物 | 检查后分别重试或继续 |
| transient-read / action-error | 工具失败 | 输入是否被改变 | 安全重试或修正动作 |
| partial-write / no-write | 返回失败 | 是否存在私有不完整文件 | 拒绝残片，重新提交 |
| late-result / cancelled | 旧 worker 返回结果 | lease 是否仍有效 | 拒绝迟到结果 |

每种干预都要提供可复现种子、状态快照和故障注入点。状态快照必须包含文件系统、提交回执、输入摘要和运行器状态；不能只保存自然语言历史。

## 数据与来源计划

第一版建议至少 6 个独立公开来源，分为训练、开发、最终测试三组，每组来源完全不交叉。优先覆盖：

- 含缺失和混合类型的回归表；
- 类别不平衡和类别清理任务；
- 时间序列或有序滚动统计任务；
- 具有异常值、重复行和部分空列的真实表；
- 至少一个中文列名或非英语值的派生任务。

每个来源保存下载地址、DOI、许可、原始档案 SHA-256、转换脚本、转换后 CSV SHA-256 和字段映射。训练过程中只能使用训练来源；最终测试来源只在协议冻结后打开。

## 指标体系

单一成功率不足以反映安全恢复，FaultDA-Bench 采用分层指标：

1. **最终正确率**：独立验证器确认答案、产物、输入未污染和显式结束。
2. **恢复成功率**：发生故障后最终恢复成功的任务簇比例。
3. **状态识别准确率**：对提交状态、输入完整性和回执一致性的判断。
4. **重复副作用率**：重复写入、重复提交、覆盖正确产物和接受迟到结果的比例。
5. **安全失败率**：无法确定状态时是否选择检查或保守终止。
6. **泛化差值**：新来源、新措辞、新故障和新工具组合相对开发集的下降。
7. **资源成本**：模型 token、工具调用、分支执行数、GPU 时间、墙钟和峰值显存。

统计单位优先使用“来源×任务意图”任务簇。四种故障是同一任务的相关重复，不能当作四个独立样本计算显著性。报告宏平均、每来源结果、最差簇和按种子配对差异。

## 基线与赛道

基准首版提供可复现基线：专家 oracle、规则恢复器、V5 当前 SFT、原始 GRPO、V5.0.15-beta.2 候选策略，以及一个不读取状态回执的故障盲策略。后续可增加 DeepSeek、Qwen、开源工具调用模型和 API 模型，但所有模型必须使用同一工具协议和同一验证器。

建议分成三个赛道：

- **Closed-weight Agent**：允许本地训练，提交权重摘要、运行日志和结果文件。
- **Prompt-only Agent**：不更新权重，只提交提示、工具适配器和结果。
- **System Reliability**：重点比较隔离、租约、取消、恢复和去重，不排名模型能力。

禁止把测试集提示、故障标签、oracle、最终答案或评测脚本内部路径传给 Agent。所有提交必须通过独立 runner 复跑，runner 记录 Git 提交、协议摘要、模型摘要和结果摘要。

## 版本路线

**beta.2 收尾阶段（当前仓库）**：完成 V5 的恢复 RL 训练矩阵、留出评测和失败分析；修正训练器、验证器及文档，不修改已冻结测试任务。

**FaultDA-Bench alpha.1**：创建 `faultda-bench` 分支，抽取 6 个来源、四类任务形态和四类故障；实现协议 schema、独立 runner、状态机验证和专家全通过门槛。

**alpha.2**：加入更多状态不确定性、跨语言改写、进程崩溃和迟到结果；提供规则基线和 V5 SFT/GRPO 基线，完成资源成本记录。

**beta.1**：扩展到至少 6 个最终测试来源，冻结公开 leaderboard 协议，加入任务簇 bootstrap 区间、最差来源门槛和提交复现包。

**1.0**：发布数据卡、任务卡、评测器、基线权重摘要、结果 schema、许可证清单和可审计排行榜；任何新来源或新故障通过版本化协议加入，不能覆盖旧测试集。

## 成功标准与风险

FaultDA-Bench 的首要成功标准是能稳定区分以下四种情况：模型选错工具、模型重复副作用、环境发生故障、模型在不确定时安全检查。若不同基线在所有任务上都接近满分，优先增加组合深度和状态不确定性；若专家无法稳定通过，先修复环境和 oracle，不能用模型结果掩盖基准错误。

主要风险是故障模拟过于理想化、任务簇过少、验证器泄漏答案、数据来源授权不清和把相关故障重复误当成独立证据。每次发布都必须保留原始输入、转换脚本、协议摘要、故障种子和完整运行日志。
