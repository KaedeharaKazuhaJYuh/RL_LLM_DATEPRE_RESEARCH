# V5.0.10 性能路线：批量生成先行，RL 训练随后接入

状态：V5.0.10 已发布；此文档保留 2026-09-30 的性能原型、测量方法及门槛，最终结果见 [V5.0.10 发布审计](V5_0_10.md)。批量推理满足本负载速度目标，但未通过逐步动作一致性门槛，仍不是默认效果评测路径。

## 为什么先优化推理

此前同机三次剖析的完整 48 题干净评测，模型生成中位数 88.74 秒、工具执行仅 0.435 秒，见 [V5 alpha.1 剖析](V5_ALPHA_1.md)。C++ 滚动均值在大表有真实收益，但不能给这种小表 LLM 评测带来数量级改善。当前最有希望的系统改造是让一个常驻 GPU 模型同时处理多个独立 episode 的下一步动作，而不是为每一步做一次 batch=1 的 `generate`。

## 已实现的可选原型

`experiments.v4_llm_eval --batch-size N` 以固定顺序分批建立互不共享产物目录的环境。每轮把未结束 episode 的 prompt 左填充成批，带显式 attention mask 做贪心生成，然后各自执行工具、更新状态和判定。`N=1` 保留原串行生成，且此次重跑的结果文件 SHA-256 与 V5 alpha.1 原完整评测相同。批处理的来源、模型、适配器、题目顺序和故障配置由 `research.v5_batch_audit` 核对；审计逐 episode 比较原始模型文本、动作、解析错误、最终通过与奖励，而不只比较通过总数。所有模型运行都在本机 CUDA 上完成，没有使用 API。

完整干净开发负载：DeepSeek-R1-Distill-Qwen-1.5B BF16、既有 SFT 适配器、48 题、197 次串行动作生成；包含模型加载和结果写入，启用相同的 CUDA 同步 profiler。`model_generate` 是嵌套阶段，不能与总墙钟相加。下表中 `N=1` 和 `N=16` 各有三次独立进程运行，列出中位数；`N=4/8` 只有单轮探索测量。

| 模式 | 总墙钟 | 相对串行 | 模型生成调用 | 峰值 CUDA 已分配 | 逐题原始输出完全一致 | 通过 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 串行 `N=1` | 88.61 秒 | 1.00× | 197 | 3.64 GB | 基线 | 36/48 |
| 批量 `N=4` | 34.42 秒（单轮） | — | 52 | 3.75 GB | 47/48 | 36/48 |
| 批量 `N=8` | 23.52 秒（单轮） | — | 27 | 3.90 GB | 47/48 | 36/48 |
| 批量 `N=16` | 17.58 秒 | 5.04× | 14 | 4.20 GB | 47/48（三轮均如此） | 36/48 |

`N=4/8` 的单轮结果分别比其同轮串行 102.21 秒快 2.97×、4.35×，不能与表内串行中位数 88.61 秒混算。三轮 `N=1` 分别为 102.21、82.61、88.61 秒，`N=16` 为 17.58、19.03、17.23 秒；中位数之比为 5.04×，逐轮配对为 5.81×、4.34×、5.14×。三轮串行结果 JSON 的 SHA-256 都与旧 V5 alpha.1 基线相同；三轮批量运行的输出差异也固定在同一题。查看[串行重复审计](v5_0_10_serial_repeat_audit.json)、[批量重复审计](v5_0_10_batch16_repeat_audit.json)及[三轮逐题对照](v5_0_10_batch16_full_r1_audit.json)。其余两轮逐题对照为 [r2](v5_0_10_batch16_full_r2_audit.json)、[r3](v5_0_10_batch16_full_r3_audit.json)。这些是已见开发负载的系统测量，不是新模型验证。

三个批量设置都在同一题的中间动作上与串行不同，最终该题两边均失败。**相同通过率不足以证明相同行为**；批量前向可能改变临界 token 的数值选择，具体机制尚未定位。因此批量生成目前是可选的吞吐实验路径，不能代替模型效果研究的串行金标准。审计文件和模型原始输出保存在 Git 忽略的 `work/v5_0_10_*`，正式报告将提交不含本机权重的可复核摘要。

另在已经使用过的来源留出协议前 4 题、四种故障条件共 16 个 episode 上，`N=16` 与串行 **16/16 逐步输出完全一致**、均通过 15/16；墙钟 42.29 秒降至 19.42 秒，约 2.18×，峰值 CUDA 已分配 4.23 GB，见[故障切片审计](v5_0_10_batch16_fault_probe_audit.json)。这个小切片仅运行一次，用于故障路径回归，不是新的模型泛化测试。

## V5.0.10 发布门槛

1. 固定完整 48 题和四故障切片，记录模型/适配器/协议 SHA-256、设备、batch 大小、CUDA 同步计时、显存峰值和逐题对照；候选设置至少三次独立进程重复。优先目标是完整负载端到端中位数 **≥3×**、峰值已分配显存 **<6 GB**；本次开发集已达到速度/显存目标，但四故障切片和新模型仍需扩展重复。
2. 若批量路径要用于**冻结模型评测或训练奖励**，必须达到逐步原始动作、终局结果与串行 100% 一致，或建立事先冻结的容差、差异归因与独立质量门槛；绝不把 batch 差异当成 RL 模型提升。未通过时继续保留 `N=1` 为默认，批量只用于明确标记的吞吐试验。
3. 针对不同 prompt 长度、失败重试、超时与部分写入运行完整回归；核对每个 episode 的产物目录隔离和计时上限。通过后再考虑按长度分桶、动态补位和跨作业模型常驻。每增加一项调度优化，都要在相同负载上重新测总墙钟及行为差异。
4. 把 batch 配置、模型/适配器摘要和设备写入 Go 作业清单及产物元数据，使调度器不会把不同推理语义的结果误合并；后续 RL rollout 可复用批量生成器，但要单独验证旧策略对数概率、参考策略、奖励分组和 PPO 更新轨迹。训练吞吐与样本效率分开报告。
5. NPU 暂用于已接入的量化推理比较。先在相同权重、相同 prompt 与量化设置下验证动作和通过率，再测含编译及不含编译的延迟；不能把旧 NPU INT4 结果直接与本次 GPU BF16 数字相除。

## 与模型研究并行的工作

性能改造不改变 V5.0.10 的主要科学问题：从**训练来源内部**增加同义改写、类别规范化和故障恢复样本，先冻结全新 prompt 与第三个公开来源，再比较等预算 SFT 与 RL，并检查跨来源、跨措辞的逐题回退。既有来源留出和新措辞诊断都已被看过，只能当回归集。若性能门槛先达到而模型门槛未达到，报告系统速度改进和模型负结果，不以速度替代 RL 效果证明。

## 复现入口

在本机已有模型与适配器时，串行和批量命令只相差 `--batch-size`；每次使用全新的 `--out` 与 `--profile-out` 文件名。`research.v5_batch_audit` 接受两个结果 JSON、两个 profile JSON 和独立输出路径：

```powershell
work/.venv-v4-llm/Scripts/python.exe -m experiments.v4_llm_eval --protocol tasks/v4/llm_hard_v1 --model work/modelscope_deepseek_r1_1p5b --adapter work/v4_llm_hard_sft_100_001/adapter --out work/serial.json --profile-out work/serial_profile.json
work/.venv-v4-llm/Scripts/python.exe -m experiments.v4_llm_eval --protocol tasks/v4/llm_hard_v1 --model work/modelscope_deepseek_r1_1p5b --adapter work/v4_llm_hard_sft_100_001/adapter --batch-size 16 --out work/batch16.json --profile-out work/batch16_profile.json
work/.venv-v4-llm/Scripts/python.exe -m research.v5_batch_audit work/serial.json work/serial_profile.json work/batch16.json work/batch16_profile.json --out work/batch_audit.json
```
