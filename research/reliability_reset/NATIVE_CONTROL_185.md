终态检查确认：记录数和 ID 集合不变，名称多重集相同，两条记录改变；创建时间保持各自原值，**完整内容哈希集合不同**。原 ID 关系链接保持不变，但按名称读取的关联视图已改变。原评分器仍检出了变化。见 [NATIVE_EFFECT_CHECK_185.json](evidence/1.0.85/NATIVE_EFFECT_CHECK_185.json)。实际 API 写入经过原 ORM 并更新哈希，本版不再只使用人工不透明哈希标签。

这说明“名称集合不变”不足以代表“完整记录内容集合不变”。本轮三次更新并未完成全字段身份交换；不能把上版隔离的 ID 置换软件控制，直接当成这条合法工具路径已经能够达到的状态。其他资源、其他操作组合和身份问题没有因此被证明正确或错误。

## 启动失败与兼容配置

在独立 Python 3.12.14 环境中，最初按声明范围解析最新依赖，连续暴露三项启动问题。均发生在完整环境初始化／任务评分之前，原件保留，没有记成模型失败或三条任务轨迹。

| 失败层 | 实际原因 | 最小修正 |
| --- | --- | --- |
| 导入 | Pydantic 2.14.1 的内部 `match_type` 参数变化，与上游 datetime 适配不兼容 | 固定 `pydantic==2.12.0` |
| 数据库载入 | SQLAlchemy 2.1.6 将数据库 URL 中的字符转义，上游代码按未转义字符串解析 | 固定 `SQLAlchemy==2.0.43` |
| API 构建 | FastAPI 0.162.0 不再接受上游使用的 Path 参数 | 固定 `fastapi==0.117.1`、`starlette==0.48.0` |

上述配置均满足原项目声明范围，最终 `pip check` 无依赖冲突。未补丁上游源码、评分器或受保护应用。数据库问题最初被怀疑与 Windows 分隔符有关；最小复现将根因定位为 SQLAlchemy URL 转义，固定版本即可在本机 Windows 跑通，无须改变系统功能。启动记录见三个 `*_COMPATIBILITY_185.json`。

版本选择与源码核验依据包括 [Pydantic v2.12.0 原实现](https://github.com/pydantic/pydantic/blob/v2.12.0/pydantic/_internal/_generate_schema.py)及 [SQLAlchemy 2.1 的 URL 行为变更](https://docs.sqlalchemy.org/en/21/changelog/migration_21.html)。这是一套已在本机核验的依赖快照，不声称覆盖其他系统或所有任务。

## 重放中保留的失败：低层评分缓存

首次复算在同一进程中先后对两个实验调用低层 `evaluate_task`，第二次错误地读到同任务已有的内存状态，变体分数与预期不符，被本地一致性断言拦截。[原 evaluator L511–512](https://github.com/StonyBrookNLP/appworld/blob/42b5bcf3cd334fee33f0c37c02070a9f5807add5/src/appworld/evaluator.py#L511-L512) 明确保留缓存以支持仍打开的 AppWorld；[官方 evaluate_tasks L525–555](https://github.com/StonyBrookNLP/appworld/blob/42b5bcf3cd334fee33f0c37c02070a9f5807add5/src/appworld/evaluator.py#L525-L555) 则提供入口空缓存检查和逐任务清理。

本版将其登记为**本地重放脚本的生命周期错误和低层接口边界**，不在事后将它改成研究主张。没有证明官方推荐批量评测流程产生误判，也没有发现模型利用该现象。失败记录未删除，见 [NATIVE_SCORE_REPLAY_185.json](evidence/1.0.85/NATIVE_SCORE_REPLAY_185.json)。

修正后的公开[重放工具](native_replay185.py)为每个对照启动独立原生进程，执行前核验 37 份输入原件及 5 份关键评分源码，要求返回全部原测试并与冻结分数一致。两次独立进程复核均与实跑吻合；最终工具也实际执行通过，见 [NATIVE_BOUND_REPLAY_185.json](evidence/1.0.85/NATIVE_BOUND_REPLAY_185.json)。新增 6 项软件测试覆盖缓存污染式假成功、缺失／重复输出、错误臂、删测试、输入被改和子进程失败；这些测试不是新增任务证据。

本轮完整评分调用共 **8 次**：两次主实跑、两次失败的同进程复算、两次修正后的独立进程复算、两次最终工具复核。完成的原生环境／轨迹为 **2 条、同一个任务**，新模型 API 调用为 **0**；重复评分不增加任务数。

## 本版决定

关闭“这条合法名称交换路径能骗过原生完整评分”的候选。1.0.75 合成反例和 1.0.80 的单起点排除结论均保留，不改写历史分数。本版的实质进展是完成了真实原生工具、原始完整评分和受约束重放这一证据链，并得到一个明确负结果。

没有 RL／模型提升、新恢复算法、跨任务规律或系统排序结论。科学状态仍 HOLD。后续不扩这条已失败的名称交换对照；新的实跑必须来自有具体原生契约依据的不同候选，否则应转入证据整理与研究决策，而不是继续靠换任务增加版本。工程验证见 [VALIDATION_185.json](VALIDATION_185.json)。
