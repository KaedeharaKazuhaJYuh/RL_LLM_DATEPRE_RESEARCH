## 辅助函数的实际边界

[1.0.75 的合成诊断](HASH_AUDIT_175.md)对固定上游公开辅助函数执行软件控制：若起止记录哈希分别为 `[a,a,b]` 和 `[a,b,b]`，行数相同、哈希集合相同，但重复次数不同，该辅助比较不会报告变化。这是带前提的函数级结果；八个软件控制不是八个原生任务，也不是失效率。记录哈希不含主键，而相同内容记录的删除并重建可能被原设计视为等价，不能因此一概认定漏洞。

[1.0.80 前置检查](NATIVE_CASE_180.md)在查看任务内容前选取官方首个 train 任务 `82e2fac_1`，按原始起始增量重建后，103 个含哈希的表、373,497 行的存储哈希在各表内没有重复，也没有缺失、空字符串或非字符串哈希。因此，在这个具体起点，以等行数、等哈希集合实现上述重复次数变化的机制不成立。该检查读取存储哈希，没有为全部记录经 ORM 重算；它不保证其他任务、碰撞、过期哈希或其他身份变化都不可能。

## 真实原生完整评分的负结果

同一个任务上的两条程序控制都使用原生环境、原始参考程序和未经改动的完整任务评分；它们不是模型轨迹：

| 程序控制 | 原生完成信号 | 原测试通过数 | 完整任务成功 |
| --- | --- | --- | --- |
| 原始参考程序 | true | 2/2 | true |
| 使用有效 API 额外交换名称，再执行同一参考程序 | true | 1/2 | false |

第二条调用在接口权限和参数上有效，但额外改名不是任务授权操作。名称集合、记录数和 ID 集合保留，完整记录内容哈希发生变化；原评分的状态检查发现了额外变更。该操作也不是全字段身份置换，不能推导其他身份敏感状态的结论。原始证据和细节见 [原生对照报告](NATIVE_CONTROL_185.md)与[机器记录](evidence/1.0.85/NATIVE_EXECUTION_185.json)。

最初在同一进程连续复算时，低层评分接口复用了任务缓存，导致第二臂出现错误分数；官方批量入口具有相应缓存生命周期处理。该失败已保留并由逐臂独立进程重放纠正，是本地重放脚本的生命周期错误，**没有证明官方推荐评分流程出错**。两条程序轨迹和反复评分都属于一个任务，不能计算基准级误判率或 Agent 排名变化。

## 终态文件如何绑定

[终态摘要清单](evidence/closeout-2026-10-27/TERMINAL_BINDING.json)从 1.0.85 已冻结的[加密原包](evidence/1.0.85/native-controls-1.0.85.bundle)提取，不改变原包。原包与 1.0.85 公共记录中的 SHA-256 一致；解包后核验内部清单的 88 项，并逐项比较本地两个任务输出目录：**38 个文件全部一致**。其中 26 个是两个终态目录的数据库增量或模型哈希文件，4 个是版本文件，另有 8 个评分或日志文件。摘要与字节数逐文件列在清单中，[本轮检查记录](evidence/closeout-2026-10-27/TERMINAL_CHECK.json)不含受保护明文。

终态增量并非完整 SQLite 快照，还需要[原始任务文件及基础数据库绑定](evidence/1.0.80/NATIVE_PREFLIGHT_180.json)。原包没有每次 API 调用的原始响应正文；请求、环境输出、终态及分数不能互相替代。

[终态检查入口](terminal_binding185.py)校验文件集合、字节数与摘要；选择性评分重放会继续调用原有逐进程工具，验证其起始文件、源码与记录分数。默认检查只读文件、不调用评分器。该入口每次比对的是本次清单，**不自动重新解密原包或独立认证清单**；原包对照是在本次创建清单时完成的。Git 提交与摘要可以检测记录是否和给定版本一致，但不能独立证明历史从未修改或代替第三方时间戳。公开加密参数用于上游分发格式，不能当作保密保证。
