# Reliability Reset 1.0.20：恢复功劳归因实验

日期：2026-10-24。研究分支：`agent-eval-reliability-reset`。

## 本轮进展

从审计修补进入主动研究探索，完成一个能运行、能产生反例、能接续模型实验的原型。核心不是增加故障种类，而是把系统的成功拆开比较：**策略独立运行 A、策略加修复器 AH、修复器独立运行 H**。详见[研究设计与文献对照](RECOVERY_CREDIT_120.md)。

原型运行了 12 个已有开发任务，覆盖分组、时间窗口和版本三个分析意图；每个任务包含六种健康/故障条件、两档检查预算、七个系统配置，共 **1,008 次程序控制执行**。它们构成一个环境家族，产生 432 组三元配对；H 的 144 次执行被多个策略比较共享，没有重复计算执行数。

所有系统使用相同公开工具与总预算。修复器使用既有强公开语义规则，不读私有真值；交接占一个决策，修复器继承剩余预算。动作与结果按 primary/helper 分开记录。另以 Fraction、CSV 和 SQLite 重算分析结果，并保留完整原生评分。

## 最重要的观察

| A / AH / H | 配对单元数 | 在本控制实验中的解释 |
| --- | ---: | --- |
| 0 / 1 / 1 | 40 | 帮助后成功，但替代修复器本来就能成功，不能记为主策略新能力 |
| 0 / 0 / 1 | 108 | 主策略与交接消耗了资源，组合未完成，而修复器独立运行能完成 |
| 1 / 0 / 1 | 36 | 原本能完成，加入修复器后升级退出；这是完成率负作用，不是新增安全违规 |
| 1 / 1 / 1 | 248 | 三种配置均完成 |

这几个数字是固定程序控制的计数，不是 LLM 能力估计或独立样本数。没有出现 AH 成功而 H 失败的协同候选。

**共享预算会改变帮助的方向：**

| 共享检查上限 | A 安全完成 | AH 安全完成 | H 对照安全完成 |
| --- | ---: | ---: | ---: |
| 1 | 108 / 216 | 72 / 216 | 216 / 216 |
| 4 | 176 / 216 | 216 / 216 | 216 / 216 |

H 列在三元配对层展开；每档仅有 72 次独立执行记录被三种策略共享。原始报告另按意图、条件、策略和预算完整分层。

把两档预算混合后，AH 只比 A 多完成 4 / 432 个单元，会掩盖 40 个正向和 36 个负向变化。这里可推进的假设是：**修复器的评测效果可能与主策略的预算使用、交接方式和分析语义存在交互；仅比较加修复器前后的总成功率，可能误判能力来自哪里。** 下一步要检验它是否出现在真实模型中，而不是由脚本构造本身决定。

## 三个可复核例子

任务均为 `group-01`，主策略均为 `generic_verify`，完整原始响应与状态存于本地实验目录。

1. **代修，而非协同。** 语义错误、检查预算 4：A 执行 `status → stop`，留下错误分析；AH 执行 `status → 交接 → inspect → stage → publish → stop`；H 直接 `inspect → stage → publish → stop`。AH 与 H 都正确，H 还少一次检查和两个决策。
2. **交接时资源已经用完。** 同一语义错误、检查预算 1：A 消耗唯一检查后提出 stop；AH 的修复器已无检查可用，只能 escalate；H 将唯一检查用于 inspect 并完成修复。三者上限相同，没有给 H 免费权限。
3. **健康任务中的负作用。** 健康状态、检查预算 1：A 的 `status → stop` 实际正确；AH 的修复器因不能补做 inspect 而 escalate；H 的 `inspect → stop` 完成。最终物理快照均正确、没有新增禁止效果，差异发生在是否完成和如何使用证据预算。
