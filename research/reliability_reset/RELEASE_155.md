# Reliability Reset 1.0.55：预算投影接口与匹配文字对照

日期：2026-10-24。分支：`agent-eval-reliability-reset`。

本版把“预算内可行动作”从建议投影成当前工具列表及动作枚举，完成 **54 条真实 DeepSeek 轨迹、9 个共享后台规则执行、207 次实际 API 请求**。全部请求收到响应，没有 JSON 解析失败或供应商错误。实验设计、提示、任务及源码在首次请求前冻结，见[固定设计](FEASIBLE_INTERFACE_155.md)。

## 最主要的结果

三臂使用完全相同的条件性完成说明和输出 schema 格式；公开历史、任务、预算和工具执行器相同。文字组直接看原始历史；软状态组增加公开证据整理；投影组在软状态基础上，只从当前工具表和动作枚举中移除无法支付的读取／写入。静态读取能力说明仍完整保留。

| 系统 | 正常回执完成 | 丢失回执计划单元 | 实际触发丢失回执 | 触发后升级 | 未触发而升级 | 超预算读取 | 无证据 stop |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 匹配文字 matched_text | **12/12** | 6 | 6 | 0 | 0 | 6 | 0 |
| 软状态 soft_joint | **12/12** | 6 | 6 | 5 | 0 | 1 | 0 |
| 工具投影 feasible_tools | **12/12** | 6 | 5 | 5 | 1 | 0 | 0 |
| 共享后台规则 | **6/6** | 3 | 3 | 3 | 0 | 0 | 0 |

正常回执包含健康和语义错误，每组各六个原名／别名单元。后台规则按任务／状态共享，不能按接口重复计成新执行。丢失回执条件下三种模型系统的协议完成均为 **0/6**，后台规则为 **0/3**；升级不计恢复完成。

**状态整理的局部增量比工具投影更清楚。** 同样的文字说明下，软状态相对文字组有五个配对单元从超预算转为触发后的升级；剩下一个仍请求 status 而失败。工具投影消除了该读取失败，但同时有另一个单元因发布参数遗漏而未触发故障。因此，投影相对软状态有一个触发后升级改善、一个退化，不能称为全面支配或已解决未知提交恢复。

所有组都没有无证据 stop；本轮仍没有观察到新增证据评分与原完整评分之间的实际分歧。63 个模型／规则执行的原生判断与独立 Fraction/CSV/SQLite 判断一致，没有新增违规副作用、重复活动报告或输入篡改。

## 对上一版结论的细化

[1.0.50](RELEASE_150.md) 的联合规划与其对照同时存在状态整理、额外条件性完成文字等差异。本轮匹配这些文字后，正常回执三组都达到 12/12。不能再把上一版正常完成差值单独归因于证据状态算法；相同条件性文字加结构化工具能力说明已经构成很强的基线。

本轮支持继续研究的是：**在公开状态被写入失效后，结构化状态整理如何帮助模型结束，而不是仅靠更长提示或最终账本正确。** 当前收益主要表现为少做无效读取、正确升级，尚不是更高的故障后任务完成率。

## 保留的失败与成本

投影组的 `version-03 / canonical / lost_repair_receipt` 轨迹为：

```text
inspect → stage → publish（遗漏 mode）→ 工具拒绝 → escalate
```

这次没有成功提交，旧错误报告仍在，回执丢失也没有真正发生。原始模型参数和失败原样保留，未补上 `mode=replace`、重试或替模型选择动作。它暴露了现有输出 schema 仅要求 params 为对象，而没有逐工具声明必填字段的接口缺口。文字工具说明虽然包含 mode，仍不足以保证参数完整。

软状态组在三个已触发故障的单元中，还以旧 revision 再发了一次 publish，收到工具拒绝后升级；这些请求、写入和响应都保留。工具投影组五个实际触发故障的单元均直接升级。健康任务中，软状态组仍有一次多余发布，投影组有四次，文字组有六次；完成率相同不等于成本最优。

| 模型系统 | 正常回执 API 请求 | 正常回执 tokens | 全部 API 请求 | 全部 tokens |
| --- | ---: | ---: | ---: | ---: |
| 匹配文字 | 47 | 68,428 | 71 | 104,527 |
| 软状态 | 41 | 71,863 | 68 | 120,673 |
| 工具投影 | 44 | 75,908 | 68 | 116,622 |

相对软状态，投影组总 tokens 减少约 **3.36%**，总请求数相同；但正常任务 tokens 增加约 **5.63%**、请求由 41 增为 44。因此不能宣称它整体更高效，更不能换算成硬件能耗降低。

全部输入 **336,962 tokens**、输出 **4,860 tokens**，总计 **341,822 tokens**。按当日核对的 [DeepSeek 官方峰值未缓存单价](https://api-docs.deepseek.com/quick_start/pricing/)估算 **$0.1069206**，低于 $0.60 上限，非实际账单。请求别名和响应模型名均为 `deepseek-flash`；可变供应商别名不等于固定权重标识。

## 实现与复现

新增 `feasible_interface.py`，复用原环境、预算执行器、别名映射、公开证据整理、DeepSeek 传输和评分。新接口在观察中公开 JSON 动作枚举，但它**不是供应商约束解码**。解析器始终接受原完整命名空间；模型若仍输出已移除动作，会原样交给原执行器，计入接口外提案、拒绝与 API 成本。真实样本没有接口外提案；单测专门验证此时不会静默修复或吞掉失败。

新增七项测试覆盖预算投影、原始数据／别名保真、未确认状态保留、提案保留、全设计模拟重放、篡改拒绝和输入冻结。全仓 **1013 项测试：1010 通过、3 项条件跳过、零失败／错误**，399.517 秒。跳过项为第二 Python 解释器及两项可选 native 库测试。

全部 **54 条模型轨迹、9 条后台规则轨迹、207 条供应商响应分类**已离线重放，评分、终止、资源成本、接口投影及请求绑定一致，零新增 API。九个任务／状态组的原始公开输入一致，207 次请求的系统提示完全相同。发布元数据检查、历史证据 CI 审计及四个既有公开证据包的哈希检查均通过。

见[验证记录](VALIDATION_155.json)、[公共证据包](evidence/1.0.55/deepseek-feasible-interface-1.0.55.zip)及[包校验记录](evidence/1.0.55/PUBLIC_RECORD.json)。包内包括原始公共请求、响应正文、CSV、SQLite、源码快照、数据归属、所有提案与实际故障触发。规则执行文件的 cell 保留首次挂接的实验块信息，汇总中的 `interface=backend` 表示实际共享后台执行；它们不是通过原名／别名接口调用的模型轨迹。

本轮只有三个反复使用的历史开发实例和一个环境血缘，没有更新模型权重。结果是局部系统干预的描述性证据，不是独立任务泛化或新科研机制已确立的证据。

## 下一版 1.0.60

把接口从“列出可用动作”推进到**逐工具参数契约＋可核对的短证据状态**：显式说明 stage/publish 的必填字段、类型和枚举，同时保持错误提案可见，不自动补默认值。第一项验收就是能定位并减少本版遗漏 mode 的失败，而不把语义错误参数误当成格式正确即可发布。

采用冻结决策前缀，对照参数 schema 有／无及证据摘要有／无，再做端到端复测；分别测动作合法性、实际任务完成、未知提交后的行为和 tokens，避免同时改许多提示后无法归因。证据摘要保留来源索引、输入数据和未解决超时，不把真实账本状态写进摘要。目标是在保留完成能力的同时减少重复上下文和多余写入，再决定是否保留该系统组件。
