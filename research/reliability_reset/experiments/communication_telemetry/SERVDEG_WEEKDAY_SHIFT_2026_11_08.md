# ServDeg 五日流量分布复核

日期：2026-11-08  
目的：检验 ServDeg 是否能提供比单日更稳定的 trace-derived 网络负载分布。  
结论：**五个相邻工作日可提供同一来源下的负载变化范围，但不支持全天、跨网络或真实包回放主张。**

## 方法与来源

- 数据：[ServDeg Zenodo 记录](https://zenodo.org/records/21983587)；随数据提供的 README 说明为 CC BY 4.0。[README](https://zenodo.org/records/21983587/files/README.md?download=1)
- 使用本机已校验的 MON.parquet；其余四天通过 DuckDB 2.0.0 `httpfs` 对 Zenodo 内容端点作 HTTP range 列式读取，没有完整下载到本地。Zenodo API 当前文件大小与 MD5 元数据均与脚本中的清单相符；远程四个文件未作本地全文件 MD5 重算。
- 每日读取 flow 数、非空时间范围、时间戳缺失行数、location 标签数、protocol 值范围、SDd/SDj 点标记率、持续事件序列率，以及包数/字节数/时长分位数。另对非空 `start_time_aggr` 按分钟分组，统计该分钟**起始的 flow cohort**；这不是该分钟内逐包速率。复算程序：[audit_servdeg_weekday_shift.py](audit_servdeg_weekday_shift.py)；机器可读结果：[JSON](SERVDEG_WEEKDAY_SHIFT_2026_11_08.json)。
- 复算命令：

```powershell
python audit_servdeg_weekday_shift.py --mon MON.parquet --output SERVDEG_WEEKDAY_SHIFT_2026_11_08.json
```

对 MON 做时间戳缺失分层后，缺失组为 1,828,437 行、有效组为 1,356,999 行。缺失组的包数 P50/P90/P99 为 1/8/230，字节数为 52/747/138,602；有效时间戳组分别为 23/91/4,416 包与 7,229/38,629/4,272,832 字节。MON 缺失组 `SDd` 标记率和 `SD_count>0` 行率均为 0；有效组为 6.330% 和 0.656%。因此缺失不是可忽略的随机删行；仅对有时间戳子集做分钟分析会系统性漏掉不同流量与标注构成。此项分层只对 MON 完成，不能外推其余四天的缺失机制。

## 研究含义与边界

- 可用作同一采集来源的**工作日负载参数范围**，或生成明确标记为 *trace-derived synthetic workload* 的背景流量统计。
- 每个文件的实际观测窗口约 42–54 分钟，并非完整 24 小时。五天来自同一个宿舍网络来源，不是五个独立拓扑或独立站点。
- `protocol=6` 全为 TCP；文件仅有聚合 flow 特征和标注，不含原始包、包级时间线、转发路径或设备/链路根因。不能声称 PCAP 回放、跨网络泛化或因果 RCA 真值。
- 点级 SDd/SDj 与持续事件序列的单位不同；它们不是同一个标签的两个等价计数器。
- `start_time_aggr` 在各日缺失 52.21%–70.49%；MON 分层显示空值组和有时间戳组在 flow 大小及 SD 标记率上明显不同。仅对有时间戳记录按 flow 起始时间分组会有选择性偏差，且其包数/字节数是 flow 累计值，不能当作该分钟内实际发送速率。缺失机制及其他四天的分层尚未审计。
- 该结果没有验证转换到 NIKA 后的速率/并发/包长保真，也没有证明强规则失效或 Agent 有增益。由于主要时间字段多数缺失，当前不把 ServDeg 用于分钟级背景流量校准；**主候选继续 HOLD；本报告不是论文贡献。**

## 下一步

ServDeg 当前不用于分钟级背景发生器：先查明时间戳缺失的生成机制，并对五天分别作缺失/非缺失特征分层。若缺失机制无法解释或恢复时间依据，关闭该数据源的时间负载校准用途。再寻找有明确许可、时间戳覆盖足够且能代表所需协议/负载的其他公开流量来源；只有来源审计通过后，才构建负载档位并测冻结规则。不得将合成流量称为真实包回放。
